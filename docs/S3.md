# Archivos: Amazon S3 en producción, MinIO en desarrollo

Amazon S3 es el **único** proveedor de archivos del back. Vive en `src/s3/`:

| Archivo | Qué hace |
|---|---|
| `s3.module.ts` | Módulo que importan `attachment`, `fleet` y `claims` |
| `s3.service.ts` | `S3Service`: `put`, `remove` y `getSignedDownload` (URL firmada con `Content-Type` y `Content-Disposition`) |
| `s3.config.ts` | Lee las variables `AWS_*` y arma el cliente del SDK v3 |
| `s3-cleanup.service.ts` | Borrado en segundo plano, reintentos y cron de huérfanos |
| `entities/storage-orphan.entity.ts` | Tabla `storage_orphan` |
| `download-link.ts`, `dto/download-link.dto.ts` | Respuesta `{ url, expiresAt, requiresAuth }` de las descargas |

No hay disco local ni un segundo proveedor: en desarrollo y en CI se usa MinIO,
que habla la misma API de S3.

Lo que guarda hoy: adjuntos de flota (`/fleet/tasks/:id/attachments`), adjuntos
genéricos de empresa (`/attachments`), la foto del reclamo (`/claims/:id/photo`) y
las fotos de entidades (ver abajo).

Principios:

- **La subida pasa por el back** (multipart): el back valida tipo (por firma del
  archivo), tamaño (10 MB) y permisos, y recién ahí sube a S3. No hay presigned
  upload.
- **El bucket es privado.** La descarga es con una **URL firmada** de corta vida
  (300 s por defecto, `AWS_S3_SIGNED_URL_TTL_SECONDS`). En la base se guarda la
  **key**, nunca una URL.
- Los objetos se suben con cifrado en reposo `AES256` (SSE-S3) y su `Content-Type`.
- **Nada queda sin dueño**: la intención se anota ANTES de la operación riesgosa
  (tabla `storage_orphan`).
  - Al **subir**, la key se reserva antes del `put` y se confirma (se quita) en la
    misma transacción que guarda la referencia. Si el proceso cae a mitad, la
    reserva queda; pasada una hora el cron borra el objeto (una reserva vieja
    significa que la referencia nunca se guardó).
  - Al **borrar un adjunto** (genérico o de flota) la baja es lógica (`deleted_at`):
    el objeto NO se borra del storage y queda de respaldo; el adjunto deja de
    listarse y de poder descargarse por la API.
  - Al **reemplazar la foto de un reclamo**, la key se anota en la misma transacción que quita
    la referencia; después se borra el objeto en segundo plano (sin bloquear la
    respuesta, con reintentos de 1 s, 5 s y 30 s) y, si sale, se quita la fila.
  - El **cron horario** reintenta lo pendiente en orden de turno con backoff
    (1 h, 2 h, 3 h... hasta 24 h). A los 24 intentos la fila pasa a `failed` y
    queda un `ERROR` en el log con la key y el motivo: hay que borrarla a mano.
    Para revisarlas: `SELECT storage_key, last_error FROM storage_orphan WHERE status = 'failed'`.
- `expiresAt` de las URLs firmadas es el menor entre el TTL y la expiración de las
  credenciales temporales (rol IAM), si las hay.

## Desarrollo con MinIO

```bash
docker compose up -d minio minio-init   # sólo los servicios nuevos; no toca la base ni Redis
```

- API S3 en `http://localhost:9000`, consola en `http://localhost:9001`
  (usuario/clave por defecto `splgminio` / `splgminio-secret`; se cambian con
  `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, y los puertos con `MINIO_PORT` /
  `MINIO_CONSOLE_PORT`).
- `minio-init` crea el bucket `splg-dev` (o `AWS_S3_BUCKET`) y termina.
- Los puertos quedan abiertos sólo en `127.0.0.1`. `minio` tiene healthcheck y
  `minio-init` espera a que esté sano (y reintenta el `mc mb`).
- Los datos quedan en `./minio-data/` (ignorada por git).
- La imagen oficial de MinIO ya no se publica en Docker Hub ni en Quay: el
  compose usa el build de Chainguard fijado por digest (`cgr.dev/chainguard/minio@sha256:...`;
  el gratuito sólo publica `latest`, por eso el digest). Se puede cambiar con
  `MINIO_IMAGE` y `MINIO_MC_IMAGE`.
- Credenciales y `MINIO_KMS_SECRET_KEY` salen de variables con un default **sólo de desarrollo**; el KMS: sin un
  KMS, MinIO rechaza el `ServerSideEncryption: AES256` que manda el back. En AWS
  no hace falta.

Variables del `.env` para que el back use MinIO:

```
AWS_S3_BUCKET=splg-dev
AWS_REGION=us-east-1
AWS_S3_ENDPOINT=http://localhost:9000
AWS_S3_FORCE_PATH_STYLE=true
AWS_ACCESS_KEY_ID=splgminio
AWS_SECRET_ACCESS_KEY=splgminio-secret
```

## Variables de entorno

| Variable | Obligatoria | Descripción |
|---|---|---|
| `AWS_S3_BUCKET` | sí | Nombre del bucket |
| `AWS_REGION` | sí | Región (`sa-east-1`) |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | no | Van juntas o ninguna. Las lee la cadena por defecto del SDK (junto con `AWS_SESSION_TOKEN` si son temporales); el back no las pasa a mano. En el VPS (fuera de AWS) van cargadas con el usuario IAM; vacías sólo si el servidor usa un rol IAM (EC2) |
| `AWS_S3_ENDPOINT` | no | Sólo MinIO / S3 compatibles (desarrollo) |
| `AWS_S3_FORCE_PATH_STYLE` | no (`false`) | `true` con MinIO |
| `AWS_S3_SIGNED_URL_TTL_SECONDS` | no (`300`) | Vigencia de la URL firmada |

Sin bucket o sin región la app **no arranca** y dice cuál falta (validación Joi
en `src/common/config/joi.validation.ts`).

## Producción: crear el bucket en la cuenta AWS de SPLG

Con el AWS CLI autenticado en la cuenta nueva (reemplazar `splg-prod-files` por el
nombre elegido; los nombres de bucket son únicos a nivel global).

### 1. Bucket privado, cifrado y versionado

```bash
aws s3api create-bucket --bucket splg-prod-files --region sa-east-1 \
  --create-bucket-configuration LocationConstraint=sa-east-1

# Block Public Access: las 4 opciones en ON
aws s3api put-public-access-block --bucket splg-prod-files \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# Cifrado en reposo SSE-S3 (AES256) por defecto
aws s3api put-bucket-encryption --bucket splg-prod-files \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

# Versionado (opcional, recomendado: permite recuperar un archivo borrado por error)
aws s3api put-bucket-versioning --bucket splg-prod-files \
  --versioning-configuration Status=Enabled
```

Obligar TLS: bucket policy que niega todo acceso sin HTTPS.

```bash
aws s3api put-bucket-policy --bucket splg-prod-files --policy '{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "SoloHTTPS",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::splg-prod-files", "arn:aws:s3:::splg-prod-files/*"],
    "Condition": { "Bool": { "aws:SecureTransport": "false" } }
  }]
}'
```

### 2. Regla de lifecycle

Limpia subidas multipart incompletas (que cobran almacenamiento sin verse) y, si
se activó el versionado, las versiones viejas:

```bash
aws s3api put-bucket-lifecycle-configuration --bucket splg-prod-files \
  --lifecycle-configuration '{
    "Rules": [
      {
        "ID": "abortar-multipart-incompletos",
        "Status": "Enabled",
        "Filter": {},
        "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
      },
      {
        "ID": "expirar-versiones-viejas",
        "Status": "Enabled",
        "Filter": {},
        "NoncurrentVersionExpiration": { "NoncurrentDays": 90 }
      }
    ]
  }'
```

### 3. Permisos IAM mínimos

Política (`splg-storage-policy`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ObjetosDelBucket",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::splg-prod-files/*"
    },
    {
      "Sid": "ListadoDelBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::splg-prod-files"
    }
  ]
}
```

`s3:ListBucket` hace falta aunque la app nunca liste. Es una particularidad de S3:
sin ese permiso, una URL firmada de una key que no existe responde **403
(AccessDenied) en vez de 404 (NoSuchKey)**. El back ya no consulta S3 para saber si
el archivo está (sólo firma la URL); el permiso sirve para que el cliente reciba un
404 claro cuando el objeto falta.

Quién usa esa política (el back de SPLG corre en un VPS **fuera de AWS**):

- **Camino principal, usuario IAM programático:** crear un usuario IAM sin consola
  con la política, generar una access key y cargarla en el `.env` del servidor
  (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`). Rotarla
  periódicamente. Nunca commitearla.
- **Alternativa, si algún día el back corre en EC2:** rol IAM con la política como
  instance profile y dejar vacías las dos variables de claves (el SDK usa las
  credenciales temporales del rol; `expiresAt` respeta su vencimiento).

```bash
aws iam create-policy --policy-name splg-storage-policy --policy-document file://politica.json
aws iam create-user --user-name splg-back-storage
aws iam attach-user-policy --user-name splg-back-storage \
  --policy-arn arn:aws:iam::<ID-DE-CUENTA>:policy/splg-storage-policy
aws iam create-access-key --user-name splg-back-storage   # sólo para el caso fuera de AWS
```

### 4. CORS (sólo si hace falta)

Abrir una URL firmada en una pestaña, un `<img src>` o un `<a href>` **no** usa
CORS. Sólo hace falta si el panel hace `fetch()`/`axios` directo a la URL firmada
(p. ej. para bajar el archivo como blob). En ese caso:

```bash
aws s3api put-bucket-cors --bucket splg-prod-files --cors-configuration '{
  "CORSRules": [{
    "AllowedOrigins": ["https://panel.<dominio-de-splg>"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["Content-Disposition", "Content-Type"],
    "MaxAgeSeconds": 3000
  }]
}'
```

### 5. Activar en el back

En el `.env` del servidor:

```
AWS_S3_BUCKET=splg-prod-files
AWS_REGION=sa-east-1
AWS_ACCESS_KEY_ID=<access key del usuario IAM>
AWS_SECRET_ACCESS_KEY=<secret del usuario IAM>
# (vacías sólo si el servidor corriera en EC2 con un rol IAM)
```

Después de correr las migraciones (`npm run migration:run`: agregan
`claims.photo_key` y la tabla `storage_orphan`, dos migraciones) y reiniciar.

## Cómo probar

- **Unit tests:** `npm test` (`S3Service` con el SDK simulado, reintentos, validación
  de config).
- **Contra un S3 real (MinIO efímero con testcontainers):**
  `npm run test:integration -- --testPathPatterns=s3.e2e`. Sube, firma, baja
  con la URL firmada (Content-Type y Content-Disposition), da de baja el adjunto y verifica el 404 (el objeto queda);
  recorre el adjunto genérico y la foto del reclamo por HTTP. Necesita Docker.
- **A mano contra MinIO:** levantar MinIO, poner las variables de arriba en el
  `.env`, levantar el back y subir un adjunto. En `http://localhost:9001` se ve el
  objeto con su key.
- **Contra el bucket real:** con las credenciales (o el rol) configuradas, subir un
  adjunto y pedir `GET /attachments/:id/download?modo=url`; la URL tiene que bajar
  el archivo y, sin la firma, `https://<bucket>.s3.sa-east-1.amazonaws.com/<key>`
  tiene que dar 403.

## Descarga: contrato para el panel y las apps

- `GET /attachments/:attachmentId/download`
- `GET /fleet/tasks/:id/attachments/:attachmentId/download`

  Sin parámetros: 302 a la URL firmada de S3.
  **Con `?modo=url`** devuelven JSON `{ url, expiresAt, requiresAuth }`, sin
  redirect. El panel tiene que usar ese modo: un 302 cross-origin hecho con
  `fetch` pierde el header `Authorization` y choca con CORS.
- `POST /claims/:id/photo` (multipart, campo `file`: JPG/PNG/WEBP, 10 MB) y
  `GET /claims/:id/photo`, con el **mismo contrato** que las descargas: por defecto
  devuelve la foto (302 a la URL firmada; si el reclamo sólo tiene una `photoUrl`
  externa vieja, 302 a esa URL; sin ninguna foto, 404) y con `?modo=url` el JSON
  `{ url, expiresAt, requiresAuth }` (`url: null` si no tiene foto).
  Pueden usarlos el cliente dueño del reclamo y los admins de la distribuidora.
  Subir o reemplazar sólo se puede mientras el reclamo no esté resuelto ni
  rechazado (409); verla, siempre. `photoUrl` en `ClaimResponseDto` pasa a ser la
  URL firmada (vence en minutos: no guardarla, pedir de nuevo).

## Fotos de entidades

Columna `photo_key` (`logo_key` en la distribuidora) con la key del objeto; en la
respuesta sale la URL firmada. Código común en `entity-photo.service.ts` y
`photo-http.ts`.

| Entidad | Endpoints (`PUT` sube/reemplaza, `DELETE` saca, `GET` 302 o `?modo=url`) | Quién | Campo |
|---|---|---|---|
| Usuario | `/users/me/photo`, `/users/:id/photo` | el propio; admin/super (el admin de empresa no toca clientes: 403) | `photoUrl` |
| Legajo | `/employees/:id/photo` (409 si tiene cuenta: vale la del usuario) | admin/super | `photoUrl` |
| Vehículo | `/car/:id/photo` | admin/super | `photoUrl` (el chofer anidado trae `user.photoUrl`) |
| Producto | `/gascylinder/:id/photo` (GET público: 404 si el producto está dado de baja, salvo para admin/super) | admin/super | `photoUrl` |
| Distribuidora | `/distributor/:id/logo` | su admin / super | `photoUrl` (logo de S3 firmado o null). `logo_url` es sólo el texto guardado; mostrar `photoUrl ?? logo_url`. `PATCH` rechaza (400) un `logo_url` que sea una URL firmada (`X-Amz-Signature`) |
| Incidencia | `/incidents/:id/photo` (409 si no está `open`) | chofer que la reportó, admin/super | `photo_url` (S3 firmada; sin foto, la externa). Un chofer ve `photo_url: null` en las incidencias ajenas de `GET /incidents/order/:orderId` |

`PUT`: multipart `file`, JPG/PNG/WEBP, 5 MB, tipo validado por magic bytes
(415 tipo inválido, 413 tamaño). Otra distribuidora: 404. La foto anterior va a
`storage_orphan` y se borra en segundo plano. Keys: `users/{id}/`,
`employees/{dist}/{id}/`, `cars/{dist}/{id}/`, `gascylinders/{dist}/{id}/`,
`distributors/{id}/logo/`, `incidents/{dist}/{id}/`.

Notas de contrato:

- `GET .../photo` sin `?modo=url` redirige (302) sólo a la URL firmada de S3. Si la entidad
  sólo tiene una URL externa (incidencia), no se redirige (open redirect): responde 200 con
  `{ url, expiresAt: null, requiresAuth: false }`.
- Al otorgar cuenta a un legajo (`POST /employees/:id/account`), su foto pasa al usuario
  (`user.photo_key`) y `employee.photo_key` queda en null; si el usuario ya tenía foto, la del
  legajo va a `storage_orphan`.
- El `down` de las migraciones de fotos anota las keys en `storage_orphan` antes de borrar las columnas.
- `seed:demo` se niega a correr con `NODE_ENV=production` o con `prod` en `DB_NAME`, `DB_HOST` o
  `AWS_S3_BUCKET`, salvo `SEED_ALLOW_PRODUCTION=true`.

## Completar las fotos de la demo

`npm run fotos:demo` deja con foto en S3, sobre los datos existentes, a los reclamos,
incidencias, productos, vehículos y al logo de la distribuidora (`SEED_DISTRIBUTOR`, por
defecto `jeny-gas`) que tienen una URL http externa, una key cuyo objeto no existe en el
bucket (HeadObject) o ninguna foto. Reserva la key en `storage_orphan`, sube con `S3Service.put`
y la confirma en la misma transacción que guarda la referencia; limpia la URL externa de la
fila. Es idempotente y no toca usuarios, choferes ni legajos. `-- --dry-run` lista lo que haría
sin escribir. Usa el mismo resguardo de producción que `seed:demo`.
